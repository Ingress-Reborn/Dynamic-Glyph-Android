5. Android 图像缓冲区处理、权限流程、OCR API 等必要平台替换不属于“重新适配识别算法”。先完成这些替换；不借机重新设计业务规则。

“沿用 iOS 参数”是首版实施策略，不代表已经验证所有 Android 设备。首版能运行、核心功能验收、完整迁移验收分别记录，不能相互替代。

## 4. 技术方案：轻量、原生、尽量少的组成部分

| 项目 | 当前实现 | 原因与约束 |
| --- | --- | --- |
| 语言 | Kotlin | 业务与识别核心统一实现，不携带 Swift 运行时或 JNI 桥接 |
| 构建 | Gradle Kotlin DSL、Gradle Wrapper | 工程固定构建版本，可在 Windows 构建 |
| 最低系统 | Android 10 / API 29 | 已写入 `app/build.gradle.kts`；系统兼容范围与实际设备验收范围分别记录 |
| compile / target SDK | API 37 | 当前构建配置为 37；不将编译成功等同于全部系统版本已实测 |
| 常规界面 | Android Views / XML，按需使用 AndroidX | 页面规模不大，先采用直接的原生实现，不并行维护两套 UI |
| Glyph 绘制 | 自定义 View + Canvas / Paint / Path | 直接画线段、槽位和状态，无视频渲染或游戏引擎依赖 |
| 屏幕采集 | MediaProjection + 单个前台 Service + ImageReader | 使用系统授权流程；不依赖 root、无障碍服务或常驻守护进程 |
| 游戏上方显示 | WindowManager 的应用悬浮窗 | 不需要把静态图形编码成视频来维持 PiP |
| OCR | 单一 ML Kit 端侧文本识别实现 | 替换 Vision；模型、裁剪与当前像素阶段调度差异明确记录 |
| 简单设置 | SharedPreferences | 小规模键值配置，不额外引入数据库或响应式设置框架 |
| 历史记录 | Room / SQLite | 已服务于真实记录、查询、统计与迁移需求 |
| 文件导入导出 | 系统文件选择器、应用私有目录、系统分享 | 不要求用户授予整个存储空间访问权限 |
| 录屏 | MediaCodec / MediaMuxer、MediaStore | 已有独立录制能力；普通识别与本次负载验收不以开启录制为前提 |

工程保持两个模块：`:app` 与 `:recognition`。后者是可直接做 JVM 测试的 Kotlin 核心，前者承载 Android 平台能力；不继续为每个功能拆 Gradle 模块。

不预先引入 OpenCV、TensorFlow、NDK、Hilt、与业务无关的网络层或自建服务器。只有真实测量说明现有实现不能满足需求时，才评估新增依赖，并记录带来的体积、维护和运行成本。跨设备结果同步是明确业务需求，可在 P4 引入其必需的系统账号、云服务和网络实现，但不得借“轻量化”删除同步，也不为此另建通用后端框架。

### OCR 的具体取舍

- 使用随包 Latin、中文、日文、韩文模型，使对应语言可在安装后离线使用，不把 Google Play 服务下载模型作为必经步骤。模型存在不等于五种游戏语言全部完成实景验收；不预建模型商店或多后端切换框架。
- 官方文档说明 bundled 模型会增加应用体积，unbundled 模型需要动态下载；最终以 Release 安装包测量为准，不能同时许诺“极小安装包”和“全部语言模型预装”。参见 [ML Kit Android 文本识别](https://developers.google.com/ml-kit/vision/text-recognition/v2/android)。
- 保留原来的裁剪、词表、文本匹配和阶段调度。Vision 特有的选项或置信度不能伪装成 Android OCR 的等价能力；适配器明确表达可取得的文本、坐标及置信信息，不凭空补高置信度。
- 首版不为此改写整套识别。出现实际 OCR 漏读或误判后，在真实输入上调整该适配边界；UI 语言与游戏识别语言分别处理。

## 6. 识别流程与通用适配原则

### 6.1 首版数据流

`MediaProjection → ImageReader → 图像入口转换 → 现有布局/节点检测 → 线条与颜色证据 → 阶段和槽位追踪 → 预测 → 显示快照 → 悬浮窗`

OCR 仅在相应阶段读取需要的区域，将结果带上源帧时间交回状态追踪。结果与掉落读取在 P4 接入同一采集流程，不另开一套屏幕采集。

- 图像入口一次性处理尺寸、rowStride、pixelStride、颜色通道和方向；内部使用统一的左上角原点坐标。
- iOS 中已使用的相对比例继续按输入图像尺寸换算；保留节点定位与缩放拟合，不能将其改为固定 Android 像素坐标。
- 第一版以竖屏游戏为目标，保留已有布局判断。未识别到的帧走现有 unknown / unavailable 状态，不能用猜测结果填满界面。
- 全屏分析只有最新待处理帧进入下一轮识别，处理落后时丢旧帧，不积压全屏队列。及时关闭 Image，控制生命周期，避免采集停止或内存持续增长。命令通知等源实现已经证明可能只出现一帧的短暂证据，保留其有界、带源时间的小裁剪队列；队列溢出、过期和断帧必须形成覆盖未知，不能把“只留最新帧”误用于这些证据。
- 识别与状态推进采用单一串行执行顺序，UI 在主线程更新；先不建立多级线程池或复杂任务调度框架。
- 活跃 Glyph 阶段先沿用约 20 Hz 的处理节奏和现有按阶段降频思路；OCR 单个在途请求，显示按变化更新。不用统一大幅降频换取表面低功耗而漏掉短暂槽位边界。

### 6.2 后续发生不适配时的处理顺序

1. 保存一个能够复现的实际失败输入，记录分辨率、内容范围、方向、采集模式和预期结果。
2. 先排除图像入口转换错误，再判断是否为沿用 iOS 区域造成的裁剪偏差，不凭设备型号推测原因。
3. 需要调整时，优先用图像中的节点阵列、已有面板/指示条特征定位游戏内容，再建立统一坐标映射。是否需要处理黑边、系统栏或宽高比，由失败证据决定。
4. iOS 比例可继续作为区域搜索的初始值；如需扩大搜索范围，增加一项有边界的通用规则，不增加机型配置表或每部手机手动填坐标的常规流程。
5. 用该失败样本、已有成功样本和不同尺寸的测试输入回归。只改动解决问题必需的部分，并记录支持范围；未实际验证的设备不宣称通过。

**禁止按 `Build.MODEL`、品牌名或某个具体屏幕分辨率选择识别参数。** “先照搬”与“后续通用识别”通过上述顺序实现，不提前建庞大的适配框架。

### 6.3 必须保留的行为

- 命令阶段的手势不混入展示序列；命令是否被游戏接受，以对应通知证据为准。
- 看到一个形状不等于确认一个槽位；沿用槽位前进或展示结束等确认边界。
- 连续重复 Glyph 不去重，漏读保留原槽位，后续项不得前移补洞。
- 输入阶段冻结期望序列；玩家画出的线条只供核验，不反向改写期望。
- 未知、观察中、已确认与预测分别表示；缺少序列表不影响已有形状识别。
- 指示条遮挡、帧间断和总槽数冲突沿用已有证据规则，不用旧画面继续冒充可靠指导。
- 核验读取抬手后的稳定样本；未知不等于错误，不在绘制过程中增加未经验证的警告。
- 结果未读到不等于游戏判错；统计和导出保留未知字段，沿用现有数值含义。

## 7. Android 系统接入要求

- 用户在可见页面点击开始，完成系统屏幕采集授权后启动前台服务，再取得投影并建立采集。通知包含明确停止入口。使用 `mediaProjection` 服务类型及对应声明，参见 [前台服务类型](https://developer.android.com/develop/background-work/services/fgs/service-types)。
- 每个采集会话重新请求系统授权；不缓存授权凭证用于重复启动。注册停止回调，在系统或用户停止时释放采集资源并撤销旧显示。屏幕尺寸变化按平台 API 更新现有 VirtualDisplay 和 Surface，参见 [Android 14 MediaProjection 要求](https://developer.android.com/about/versions/14/behavior-changes-14#media-projection)。
- 已按 `onCapturedContentResize()` 的实际内容尺寸同步更新现有 VirtualDisplay 与 Surface，参见 [MediaProjection 尺寸变化](https://developer.android.com/media/grow/media-projection)。本次验收选择共享整个屏幕；系统单应用共享和分屏到全屏悬浮窗的坐标映射仍未认证，不能从尺寸回调已实现推定通过。
- 悬浮窗使用用户授予的显示在其他应用上层权限；窗口边界紧贴可见内容，不用全屏透明窗口。保留拖动、隐藏和恢复，游戏区域触摸不被无形窗口占用。
- 不默认认为悬浮窗设置为不可触摸就一定可以穿透操作。以小窗口避让游戏操作区为初版方式，在真实设备验证；参见 [Android 12 遮挡触摸规则](https://developer.android.com/about/versions/12/behavior-changes-all#untrusted-touch-events)。
- 全屏采集可能再次看到本应用悬浮窗。窗口根据实际阵列/计时条空隙摆放及缩放，手动拖动后不再自动夺回位置；不把摆放估计当识别证据，也不承诺所有设备都能将悬浮窗排除出采集。
- 处理拒绝授权、用户取消、系统停止和正常重新开始。进程被结束后保持停止，用户重新启动时再授权，不实现后台自启动或自动恢复采集。
- 通知权限与前台服务要求分开处理，不把拒绝通知权限误写成可以省略前台服务通知。
- P5 录制游戏音频时按系统播放音频采集要求申请权限，是否可采集取决于目标应用策略；不使用麦克风来源。参见 [播放音频采集](https://developer.android.com/media/platform/av-capture)。

这些是正常平台接入和已存在的业务约束，不是新增推测性竞态机制。

## 10. 验证方法与轻量化标准

### 测试真实实现

- JVM 测试直接调用生产用 parser、predictor、像素识别和状态机。可迁移 Swift 测试的独立输入与预期结果，不能将 Swift 业务算法复制到测试里充当正确答案。
- 优先覆盖节点/路径、方向无关、同形候选、序列歧义、总槽数约束、重复项、缺槽、阶段转换、输入冻结与 CSV 未知值。

- 回放入口直接复用实时识别核心，按原始时间推进；人工标注只用于对比结果，不进入识别过程。
- Android 测试覆盖真实文件导入、数据库和显示；权限、后台采集、悬浮窗触摸、系统停止及游戏音频在真机检查，不靠 mock 宣称验证完成。

### 资源与性能

- 默认只有一个采集会话、一个串行识别流程、最新待处理帧和单个在途 OCR 请求；停止后不保留采集或识别循环。
- 避免逐帧创建整屏 Bitmap、多次颜色转换或整屏 OCR；缓冲复用依据真实热点实施，不先建立通用内存池框架。
