# Glyph Lens 0.4.6：降低单帧识别开销

更新日期：2026-11-17。生产源码 `51709f4`。

## 目标与边界

识别底层与 Auto Glyph 共用，本次只让“每一帧更便宜”，**不降低识别节奏**。按每秒 10 帧核对两段原录屏：展示阶段每个 Glyph 只亮约 0.2–0.4 秒，间隔约 0.1–0.2 秒，五图约 2 秒放完；每秒采样一次会漏图，因此展示期约 20 次/秒的分析、确认边界和预测规则都不改。

## 改动

| 位置 | 改动 | 结果是否变化 |
| --- | --- | --- |
| 整帧 11 点阵搜索 | 每隔一个“最小环高”取一行作种子，连通域按行段填充，复用缓冲；环仍按首像素的扫描顺序输出 | 不变 |
| 亮度门控 | 采样回调内联，不再装箱 | 不变 |
| 地图按钮搜索 | 搜索区域改为预先算好的整格边界，跳过区域外的行 | 不变 |
| 采集拷贝 | 引擎拆成“准入”和“分析”两段：被节奏拒绝的帧只拷贝门控采样的行，破解阶段被拒绝的帧不拷贝；被分析的帧复用上一帧的像素缓冲 | 不变 |
| 省电与温度状态 | 一次读取供随后一秒内的帧使用 | 进入省电模式或过热后的降频最多晚 1 秒 |

## 验证

- 新旧实现差分：700 个随机场景，以及从两段原录屏按每秒 2 帧抽出的 116 帧，点阵搜索、地图按钮和亮度门控的结果逐一相同。差分用的旧实现副本不留在仓库。
- 单元测试：`:recognition:test` 与 `:app:testDebugUnitTest` 全部通过。新增 4 项：采样行门控读数等于整帧读数、只拷贝采样行、缓冲复用、延迟拷贝路径与原路径的快照逐帧相同且只拷贝被分析的帧。
- Debug 真实屏幕共享 4 项通过：五图 question → less → forget → all → lie、两段三图（advance → human → enlightenment 与 nourish → xm → portal），以及返回地图隐藏后继续下一轮。
- 签名正式包 0.4.6：`autoStart`、`threeGlyph`、`map` 三项黑盒流程通过，绘制期与输入期的悬浮窗截图已人工查看，五图与三图序列图形和预期一致。

## 未证实与未覆盖

- **省电效果没有在设备上测出来。** 新旧包的 CPU 对比在 Auto Glyph 上用同一识别底层做过：模拟器上交替各跑 4 轮，每轮进程 CPU 时间都在 3.5–4.6 秒之间，同一个包两次运行的波动大于新旧之差。两段录屏大部分时间在破解画面内，而本次省的主要是地图、Portal 页等破解以外的画面。
- 桌面 JVM 上，同样的真实帧整帧点阵搜索由每帧约 2–6 毫秒降到 0.2–1 毫秒。这只说明算法本身更便宜，不等于手机耗电降幅；实体手机的 CPU、温度和电量未测量。
- 正式包的 `hidden` 与 `calibration` 两项流程本次未重跑。

正式包：`Glyph-Lens-0.4.6-arm64.apk`，417,789 字节，约 0.418 MB，沿用既有签名。本次只发布到 origin，未同步 szres/main。
